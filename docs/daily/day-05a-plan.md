## 2. The seam design — a Database Provider

Analogous to the backend-plugin seam: a technology-neutral **contract in the core**, a **Postgres implementation in `plugins/`**, selected by the composition layer from the model's `database` answer. Postgres is the *sole* provider on Day 5a.

### 2.1 Responsibility split

- **Database-agnostic (stays in the backend plugin):** entity/table/column **names**, field **order**, which columns exist (id, fields, FKs, owner, timestamps), FK/index **naming** (`fk_<t>_<target>`, `idx_<t>_<col>`), the migration-file **structure** (V-numbering, `CREATE TABLE` skeleton), the migrate-runner **logic** (read `V*.sql`, apply once), the docker-compose **structure**, and all **application code** (models, repositories, routes, auth, serializers).
- **Database-specific (moves behind the seam — the provider supplies it):** everything in §1 — the SQL **dialect** (types, auto-increment, timestamp, FK/index SQL, users-table + schema_migrations DDL) and the **environment/connection** facts (driver/dep, connection URL/scheme, Django ENGINE, Docker image/healthcheck/port).

### 2.2 The interface (core-neutral — no Postgres/MySQL words in the core)

```ts
// core/database.ts — a generic database-provider contract
interface DatabaseProvider {
  readonly id: string;          // 'postgres'
  readonly displayName: string; // 'PostgreSQL'

  // (A) SQL dialect — consumed by the SQL-migration backends' codegen
  dialect: {
    columnType(logicalType: string, opts): string;    // String/Text/Integer/Long/Decimal/Boolean/Date/DateTime → dialect type
    autoIncrementPrimaryKey(): string;                 // the id column definition
    timestampColumnType(): string;                     // e.g. "TIMESTAMPTZ NOT NULL DEFAULT now()"
    foreignKeyConstraint(table, name, col, refTable): string;
    createIndex(name, table, col, unique): string;
    usersTableDDL(): string;                           // the V1 users-table body
    schemaMigrationsDDL(): string;                     // the migrate-runner bookkeeping table
  };

  // (B) Environment/connection facts — consumed by each backend's shell
  //     (structured per ecosystem so a backend picks its slice; the provider is
  //      the single home for all Postgres facts across ecosystems)
  docker: { image: string; healthcheckTest: string; port: number };
  connection: {
    node?:   { npmPackage: [name, version] };
    python?: { pipPackage: string; sqlalchemyUrlScheme: string };
    django?: { pipPackage: string; engine: string };
    java?:   { jdbcSubprotocol: string; driverArtifact: string; flywayArtifact: string };
  };
}
```
(Exact surface is a Session-2 detail; the point is a small, generic contract whose Postgres implementation holds every string from §1.) The core defines only the shape — no dialect strings. Law 25 holds.

### 2.3 How backends consume it (the genuinely-needed wiring)

- `buildFileSet(model, backendPlugin, databaseProvider)` — the core generation entry gains a `DatabaseProvider` parameter and threads it into `generateProjectShell(model, db)` and `generateEntity(entity, ctx)` (context gains `database: DatabaseProvider`). It receives a *handle* and never learns which database — the same neutral-refinement category as Day-1's relationship representation.
- **SQL-migration backends** (Spring/Express/FastAPI): `sqlTypeOf`/`buildMigration` call `db.dialect.*` instead of hardcoding; the shell's `V1__init.sql` and `schema_migrations` DDL come from `db.dialect.usersTableDDL()`/`schemaMigrationsDDL()` (moved from static template into codegen, or the divergent lines tokenized — Session-2 choice, byte-identity is the guard either way); driver/URL/docker come from `db.connection.*`/`db.docker.*` via shell tokens.
- **Django**: consumes only `db.connection.django` (ENGINE + pip driver) and `db.docker` — its ORM migrations are untouched.
- **Composition/registry** (`plugins/database-registry.ts`): `{ 'PostgreSQL': postgresProvider }`, selected from `model.getSetting('database')` and passed alongside the backend plugin.

### 2.4 Postgres = the first (and only) provider
`plugins/database/postgres` implements the contract by returning **the exact current strings** from §1. No behavior changes — the strings move to one home.

## 7. Risk notes (for Session 2)

- **Byte-drift is the entire risk.** The `V1__init.sql` and `schema_migrations` DDL extractions are the trickiest (static template → provider-generated/tokenized) — they must reproduce the current bytes exactly (alignment, comments, trailing newlines). Diff each backend's full Postgres output, not just the hash, when a mismatch appears.
- **Do the extraction one backend at a time**, re-checking that backend's two hashes (DemoApp + TeamTracker) after each, so drift is localized and easy to bisect.
- **Interface-threading misses** — a demo/CLI/UI caller not updated will fail to compile (good) or, worse, be skipped; ensure every `buildFileSet` caller selects Postgres. The eight-hash gate is the backstop.
- **Resist scope creep** — do not "improve" any SQL or shell string while moving it; extract verbatim. Any improvement is a deliberate later change with its own re-established hash, never smuggled into a refactor.
- **Express runtime SQL** — leave `$1`/`now()` exactly as-is; it's Postgres-valid and out of scope for Day 5a.
