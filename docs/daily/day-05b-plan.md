## 0. What Day 5a already gave us (the seam, concretely)

The contract is real and small — [`generator/src/core/database.ts`](../../generator/src/core/database.ts):

- **`SqlDialect`** — 6 methods the SQL-migration backends assemble DDL from:
  `columnType(logicalType, opts?)`, `identityPrimaryKey()`, `bigInt()`, `timestampDefaultNow()`, `foreignKey(table, name, column, refTable)`, `index(name, table, column, unique)`.
- **`DatabaseProvider`** — `id`, `displayName`, `sql: SqlDialect`, and `tokens(): Record<string, string>` (flat shell-substitution tokens).
- **`postgresProvider`** ([`postgres.ts`](../../generator/src/plugins/database/postgres.ts)) holds every string verbatim; the users table is a whole-block token `__DB_USERS_TABLE_DDL__`.
- **Registry** ([`database-registry.ts`](../../generator/src/plugins/database-registry.ts)): `DATABASES = { PostgreSQL: postgresProvider }`, `selectDatabaseProvider(model)` keyed on the Phase-A `database` answer. **Adding MySQL = one line here.**
- **Token substitution** (`applyTokens`, e.g. [`python-plugin.ts:51`](../../generator/src/plugins/python/python-plugin.ts)): a global `str.split(key).join(value)` over every template file for every `__DB_*__` token. All four backends already merge `...database.tokens()` into their tokenisation, and the three SQL backends' `entity-codegen.ts` already call `ctx.sql.*` for all DDL.

**Consequence:** MySQL is a new object implementing the same contract + one registry line. The backends do not change (with one honest exception at runtime — Express, §3). This plan is "implement `mySqlProvider`," exactly as the seam intended.

**Core-neutrality note (the correction from the brief):** `core/database.ts:24` contains an illustrative `"TIMESTAMPTZ NOT NULL DEFAULT now()"` inside a JSDoc comment on `timestampDefaultNow()`. That is **documentation of the method's shape, not logic** — **leave it untouched.** Do not "fix" it into MySQL-awareness; making a doc example dialect-aware would be noise, and the core stays neutral because the string is a comment, not code (Law 25 holds — confirmed in the Day-5a report §3).

## 1. The MySQL provider — every dialect piece, mapped to its contract member

`plugins/database/mysql.ts` → `mySqlProvider`, registered as `MySQL → mySqlProvider`. Each piece below maps to the exact `SqlDialect` method or `tokens()` key it implements.

### 1.1 `SqlDialect` — the DDL primitives (consumed by Spring/FastAPI/Express `entity-codegen.ts`)

| Contract member | Postgres today | **MySQL 8** |
|---|---|---|
| `columnType('String', {maxLength})` | `VARCHAR(n)` (default 255) | `VARCHAR(n)` — same |
| `columnType('Text')` | `TEXT` | `TEXT` — same |
| `columnType('Integer')` | `INTEGER` | `INTEGER` — same (MySQL alias for `INT`) |
| `columnType('Long')` | `BIGINT` | `BIGINT` — same |
| `columnType('Decimal')` | `NUMERIC(19, 2)` | `DECIMAL(19, 2)` (`NUMERIC` is a MySQL alias; emit `DECIMAL` for clarity) |
| `columnType('Boolean')` | `BOOLEAN` | `TINYINT(1)` (what MySQL actually stores; `BOOLEAN` is its alias — emit `TINYINT(1)` explicitly per Law 44 readability of *stored* type) |
| `columnType('Date')` | `DATE` | `DATE` — same |
| `columnType('DateTime')` | `TIMESTAMPTZ` | `DATETIME` (chosen over `TIMESTAMP`: wider range, no 2038 cliff; **honest caveat: no timezone — app stores UTC**) |
| `identityPrimaryKey()` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `BIGINT AUTO_INCREMENT PRIMARY KEY` |
| `bigInt()` | `BIGINT` | `BIGINT` — same (FK / owner columns) |
| `timestampDefaultNow()` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| `foreignKey(t, name, col, ref)` | `ALTER TABLE t ADD CONSTRAINT name FOREIGN KEY (col) REFERENCES ref (id);` | **identical string** — requires InnoDB (MySQL 8 default) + referenced col indexed (PK ✓) |
| `index(name, t, col, unique)` | `CREATE [UNIQUE] INDEX name ON t (col);` | **identical string** |

Only **five** of the DDL primitives actually diverge (`columnType` for Decimal/Boolean/DateTime, `identityPrimaryKey`, `timestampDefaultNow`); `foreignKey` and `index` are byte-for-byte the same syntax. That is the whole point of the seam — the divergence is small and localised.

**`updated_at` decision (logical parity, stated honestly):** MySQL *offers* DDL-level `... DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`. We deliberately **do not** add `ON UPDATE` — `updated_at` stays app-managed exactly as on Postgres, so the two dialects have the **same logical semantics** (the app owns `updated_at`). Adding `ON UPDATE` would make MySQL behave differently from Postgres; we reject it for logical parity.

### 1.2 `tokens()` — the shell/connection facts (consumed by each backend's shell)

| `tokens()` key | Postgres today | **MySQL 8** |
|---|---|---|
| `__DB_IMAGE__` | `postgres:16-alpine` | `mysql:8` |
| `__DB_USERS_TABLE_DDL__` | Postgres users DDL block | MySQL users DDL block (§1.3) |
| `__DB_NODE_DRIVER__` / `__DB_NODE_DRIVER_VERSION__` | `pg` / `8.13.1` | `mysql2` / pinned version (e.g. `3.11.5`) |
| `__DB_PY_DRIVER__` (**FastAPI**) | `psycopg2-binary==2.9.10` | `PyMySQL==1.1.1` |
| `__DB_SQLALCHEMY_URL_SCHEME__` | `postgresql+psycopg2` | `mysql+pymysql` |
| `__DB_DJANGO_DRIVER__` (**new — see §1.4**) | `psycopg2-binary==2.9.10` | `mysqlclient==2.2.4` |
| `__DB_DJANGO_ENGINE__` | `django.db.backends.postgresql` | `django.db.backends.mysql` |
| `__DB_JDBC_SCHEME__` | `jdbc:postgresql` | `jdbc:mysql` |
| `__DB_JDBC_GROUP__` | `org.postgresql` | `com.mysql` |
| `__DB_JDBC_ARTIFACT__` | `postgresql` | `mysql-connector-j` |
| `__DB_FLYWAY_ARTIFACT__` | `flyway-database-postgresql` | `flyway-mysql` |
| `__DB_SCHEMA_MIGRATIONS_TS__` (**new — see §2**) | `TIMESTAMPTZ NOT NULL DEFAULT now()` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` |

Healthcheck/port are **not** currently separate tokens (Postgres `pg_isready`/5432 live inside the docker-compose token block via `__DB_IMAGE__` and the compose template). If the compose template hardcodes `pg_isready`/`5432` outside `__DB_IMAGE__`, they must become tokens too (`__DB_HEALTHCHECK__` → `mysqladmin ping -h 127.0.0.1`, `__DB_PORT__` → `3306`). **Session-2 first task: grep the four docker-compose templates for `pg_isready`/`5432` and confirm whether they are already tokenised.** If they are hardcoded, tokenising them (Postgres value unchanged) is required and stays byte-identical on the Postgres path.

### 1.3 MySQL users-table DDL (`__DB_USERS_TABLE_DDL__` value)

```sql
CREATE TABLE users (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    username      VARCHAR(100) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    enabled       TINYINT(1)   NOT NULL DEFAULT TRUE,
    created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```
This is a **new MySQL block** — its column alignment is its own; it does not affect Postgres bytes. `DEFAULT TRUE` is MySQL-valid (`TINYINT(1)` accepts `TRUE`/`1`). No explicit `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4` clause — both are MySQL 8 defaults; omitting keeps the DDL clean and FK-capable (InnoDB is required for FK and is the default).

### 1.4 The one token-surface refinement MySQL forces (honest)

On Postgres, **FastAPI and Django share** `__DB_PY_DRIVER__ = psycopg2-binary` — one token served both Python backends. **MySQL splits them:** FastAPI wants `PyMySQL` (pairs with the SQLAlchemy `mysql+pymysql` URL); Django's canonical driver is `mysqlclient`. So Django needs its **own** driver token, `__DB_DJANGO_DRIVER__`.

- **Change:** Django's `requirements.txt` template swaps its `__DB_PY_DRIVER__` reference to `__DB_DJANGO_DRIVER__`. Add `__DB_DJANGO_DRIVER__` to **both** providers.
- **Postgres byte-safety:** `postgresProvider.__DB_DJANGO_DRIVER__` returns the *same* `psycopg2-binary==2.9.10` string Django emits today → **Django Postgres output stays byte-identical.** This is a token-surface refinement with zero Postgres output change, guarded by the eight-hash gate.
- **Day-6 live-boot caveat (not a Day-5b blocker):** `mysqlclient` needs `default-libmysqlclient-dev` to build; the Django MySQL image may need that dep at live-boot. Flagged for Day 6; Day 5b is generation-only, so the driver string only needs to be deterministic.

## 2. The `schema_migrations` residual — extract it dialect-aware, Postgres byte-identical (PREFERRED path, decided)

**The residual (from Day-5a report §3):** the two custom migrate-runners still hold their bookkeeping DDL inline, with a Postgres-specific timestamp:
- Express — [`migrate.js:15`](../../generator/plugins/express/templates/src/migrate.js) — one line:
  `'CREATE TABLE IF NOT EXISTS schema_migrations (version VARCHAR(255) PRIMARY KEY, applied_at TIMESTAMPTZ NOT NULL DEFAULT now())'`
- FastAPI — [`migrate.py:20-22`](../../generator/plugins/python/templates/app/migrate.py) — a 3-line concatenated Python string literal ending `"applied_at TIMESTAMPTZ NOT NULL DEFAULT now())"`.

Day 5a left these inline because the FastAPI one is a 3-line concatenation and collapsing it to a single-line whole-DDL token would have moved bytes → moved the FastAPI hash.

### The decision: byte-identical extraction (no baseline re-establishment needed)

The **only** dialect-divergent span in either file is the contiguous substring **`TIMESTAMPTZ NOT NULL DEFAULT now()`** — identical text, contiguous, in both files. Everything else (`CREATE TABLE IF NOT EXISTS schema_migrations (`, `version VARCHAR(255) PRIMARY KEY,`, `applied_at`) is standard SQL, byte-identical across both dialects.

Because `applyTokens` is a global substring replace, we tokenise **only that substring**:

- Add token **`__DB_SCHEMA_MIGRATIONS_TS__`** to both providers:
  - Postgres → `TIMESTAMPTZ NOT NULL DEFAULT now()` (**exact current bytes**)
  - MySQL → `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`
- In `migrate.js`, replace the literal `TIMESTAMPTZ NOT NULL DEFAULT now()` with `__DB_SCHEMA_MIGRATIONS_TS__`.
- In `migrate.py`, replace the same substring **inside the existing third fragment** — the 3-line physical structure is preserved untouched; only the substring changes.

**Result on Postgres:** after substitution both files are **byte-for-byte what they are today** (the token expands to the exact original string). No hash moves. **This is the preferred outcome the brief asked for — the extraction produces identical Postgres output, so no baseline is re-established and nothing is silently changed.** On MySQL the same span becomes valid MySQL DDL.

**Why not a whole-line `__DB_SCHEMA_MIGRATIONS_DDL__` token?** It would force FastAPI's 3-line concatenation onto one line → byte drift → exactly the hash-move Day 5a avoided. The substring token sidesteps that entirely. Reject the whole-DDL token.

**Substitution-safety guard (Session-2 note):** `__DB_SCHEMA_MIGRATIONS_TS__` and the existing `timestampDefaultNow()` share the same Postgres text `TIMESTAMPTZ NOT NULL DEFAULT now()`, but the users-table block is injected via `__DB_USERS_TABLE_DDL__` (whose *value* contains that text, not the *key*), and `applyTokens` matches keys not values — so there is no cascade/double-substitution risk. Confirm by diffing the two migrate files after extraction.

**Net:** the residual is closed, dialect-aware, and Postgres stays frozen. No documented baseline re-establishment is required. (If, contrary to analysis, an exact byte reproduction proved impossible for one file, the fallback would be an explicitly-flagged, documented re-baseline of that single hash — **never silent** — but §2's analysis shows it is not needed.)

## 3. Scope — which backends get MySQL on Day 5b (honest effort)

The seam covers **DDL + connection/driver/image tokens**. It does **not** cover **runtime query SQL** (placeholders, runtime `now()`). That line divides the backends:

| Backend | Runtime SQL | MySQL cost given the seam | Day 5b? |
|---|---|---|---|
| **Django** | ORM (dialect-agnostic) | shell/config tokens only (`__DB_DJANGO_ENGINE__`, `__DB_DJANGO_DRIVER__`, `__DB_IMAGE__`) — ORM migrations untouched | ✅ **Yes** |
| **FastAPI** | SQLAlchemy (abstracted) | DDL via `ctx.sql.*` + connection tokens — **the meaty dialect proof** | ✅ **Yes** |
| **Spring** | Hibernate (abstracted) | **same DDL shape as FastAPI** (already consumes `ctx.sql.*`) + JDBC/Flyway tokens; Hibernate auto-detects dialect from the JDBC URL | ✅ **Yes** |
| **Express** | **hand-written `$1` placeholders + `updated_at = now()` in `*.repository.js`** | needs a **runtime-placeholder abstraction** (`$1`→`?`, `now()`→`CURRENT_TIMESTAMP`) that the current DDL-only seam does **not** model | ❌ **Day 6** |

**Day 5b = Django + FastAPI + Spring.** All three have runtime SQL abstracted by their ORM/Hibernate/SQLAlchemy layer, and all three already consume the seam — so MySQL support is genuinely additive: `mySqlProvider` + one registry line + the token-surface refinements in §1.4/§2. No `entity-codegen.ts` or backend-logic edits. This is "implement the provider," not "hack the backends."

**Express → Day 6, deliberately.** Its repositories emit `$1, $2, …` (pg) and `updated_at = now()` directly in runtime code — Postgres-valid, but mysql2 needs `?` placeholders and `CURRENT_TIMESTAMP`. That is a **runtime-SQL divergence outside the DDL seam**; supporting it means extending the seam (or the Express repository codegen) with a placeholder/runtime abstraction — a focused change that deserves its own step, not a rush inside Day 5b. Express's DDL *would* already come out as MySQL via the seam, but the generated app would not run correctly, so we do **not** claim Express-MySQL on Day 5b. (Day 5a already kept Express's `$1`/`now()` byte-identical and out of scope; this continues that.)

This staging is honest: three backends prove both handling shapes (ORM-abstracted = Django; explicit-DDL-with-abstracted-runtime = FastAPI + Spring), and the one genuinely harder backend is isolated into Day 6 alongside the dropdown, cross-stack proof, and live boot.

## 4. Logical-vs-dialect honesty (same principle as the four-stack logical-vs-literal agreement)

MySQL and Postgres generate the **same logical schema** — same tables, same columns in the same order, same relationships, same FK/index **names**, same migration-file structure and V-numbering, same application code. They differ only in **dialect literals**. The concrete differences, in one place:

- **Auto-increment PK:** `BIGINT GENERATED BY DEFAULT AS IDENTITY` ↔ `BIGINT AUTO_INCREMENT`.
- **Timestamp type + default:** `TIMESTAMPTZ … now()` ↔ `DATETIME … CURRENT_TIMESTAMP` (MySQL drops timezone — app stores UTC; logical meaning identical).
- **Decimal:** `NUMERIC(19,2)` ↔ `DECIMAL(19,2)` (aliases; same semantics).
- **Boolean:** `BOOLEAN` ↔ `TINYINT(1)` (MySQL alias; same 0/1 semantics).
- **Drivers/URLs/engine/image/port:** per §1.2.
- **`schema_migrations` timestamp:** per §2.
- **Identical across both (no divergence):** `VARCHAR(n)`, `TEXT`, `INTEGER`, `BIGINT`, `DATE`; the FK `ALTER TABLE … ADD CONSTRAINT … REFERENCES` statement; the `CREATE [UNIQUE] INDEX` statement; every table/column **name**, field **order**, and the whole migration/runner/compose **structure**.

**The honest framing:** "same logical schema, different SQL dialect" — never "same SQL." We assert logical parity (which Day-6 cross-stack proof and live boot will confirm), and we enumerate the literal differences rather than hiding them. Honest MySQL caveats to state plainly in the report: `DATETIME` has no timezone (store UTC); FK enforcement needs InnoDB (MySQL 8 default); a column default must be `CURRENT_TIMESTAMP` (not `now()`); lowercase table names avoid the `lower_case_table_names` case trap (our tables are already lowercase). Django's ORM handles all of these per `ENGINE` automatically.

The hash axis is now `(backend × database × model)`.

## 8. Risk notes (for Session 2)

- **Postgres byte-drift is the #1 risk**, concentrated in exactly two places: the **`__DB_DJANGO_DRIVER__` split** (§1.4) and the **`__DB_SCHEMA_MIGRATIONS_TS__` residual** (§2). Both are engineered to expand to the exact current Postgres bytes; **diff the affected files** (Django `requirements.txt`, `migrate.js`, `migrate.py`) after the change, not just the hash. Any Postgres hash move = a token wasn't byte-faithful; fix before proceeding.
- **Token cascade guard (§2):** confirm no double-substitution where an injected token *value* contains another token's text; `applyTokens` matches keys, and our values contain SQL not `__DB_*__` keys, so it's safe — but verify by diff.
- **Don't over-tokenise the residual:** tokenise only the `TIMESTAMPTZ NOT NULL DEFAULT now()` substring, not the whole DDL — the whole-line token reintroduces the FastAPI byte-drift Day 5a avoided.
- **Resist scope creep into Express:** its DDL will emit as MySQL via the seam, but its runtime `$1`/`now()` is Postgres-only — do **not** claim or "quick-fix" Express-MySQL here; it's Day 6's focused work.
- **Django MySQL driver build-dep** (`mysqlclient` needs `default-libmysqlclient-dev`) is a **Day-6 live-boot** concern, not a Day-5b generation blocker — the string only needs to be deterministic now. Note it for Day 6.
- **Honest semantics in the report:** state `DATETIME`-drops-timezone, InnoDB-required-for-FK, and `CURRENT_TIMESTAMP`-not-`now()` plainly; assert *logical* parity, never byte-identical SQL across dialects.
