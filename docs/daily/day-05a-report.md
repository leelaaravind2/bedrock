## 1. What was extracted

A clean **database-provider seam** separating the database-specific parts of generation from the database-agnostic parts. Postgres becomes the first (and, until Day 5b, only) provider.

- **`src/core/database.ts`** — the neutral contract: `DatabaseProvider` (id, displayName, a `SqlDialect`, and shell `tokens()`) and `SqlDialect` (`columnType`, `identityPrimaryKey`, `bigInt`, `timestampDefaultNow`, `foreignKey`, `index`). No Postgres/MySQL specifics — the core knows only "a database provider."
- **`src/plugins/database/postgres.ts`** — `postgresProvider`, holding every Postgres string **extracted verbatim**: the SQL dialect (types, `BIGINT GENERATED … AS IDENTITY`, `TIMESTAMPTZ … now()`, `ALTER TABLE … ADD CONSTRAINT … REFERENCES`, `CREATE [UNIQUE] INDEX`), the users-table DDL, and tokens for the Docker image, drivers, connection URL/scheme, Django `ENGINE`, and Flyway/JDBC artifacts.
- **`src/plugins/database-registry.ts`** — `selectDatabaseProvider(model)` maps the Phase-A `database` answer to a provider (Postgres today), injected into each backend factory via the backend registry. Backend factories default to Postgres, so direct callers are unaffected.
- **All four backend plugins refactored** to obtain database-specific pieces from the provider: the three SQL stacks' `entity-codegen.ts` now call `ctx.sql.*` for all DDL (the triplicated `sqlTypeOf` is gone); the shells are tokenised for image/driver/connection; `V1__init.sql`'s users table comes from a provider token; Django consumes only the connection/engine/image tokens (its ORM migrations were already dialect-agnostic).

## 3. The seam is real (design + completeness)

**What a database provider is responsible for** (the dialect-specific bits) vs. what stays in the backend (the agnostic structure):

| Provider owns (dialect-specific) | Backend keeps (agnostic) |
|---|---|
| Column types; auto-increment PK; timestamp type+default; FK-constraint & index SQL | Table/column **names**, field **order**, which columns exist, FK/index **naming** |
| Users-table DDL | Migration file **structure** (V-numbering, CREATE TABLE skeleton), migrate-runner **logic** |
| Docker image; driver dependency; connection URL/scheme/`ENGINE`; Flyway/JDBC artifacts | Docker-compose **structure**; all **application code** (models, repos, routes, auth, serializers) |

**Completeness checks (this session):**
- The three SQL backends call `ctx.sql.*` for DDL (10 calls each); **no** `TIMESTAMPTZ` / `GENERATED BY DEFAULT AS IDENTITY` / `NUMERIC(19…` / `jdbc:postgresql` literal remains in any `entity-codegen.ts`.
- **No** `postgres:16` / `jdbc:postgresql` / `psycopg2` / Django `ENGINE` / `"pg"` literal remains in any shell template — all are provider tokens.
- **Core neutral (Law 25):** `src/core/` contains no Postgres/MySQL dialect logic. (The single `TIMESTAMPTZ` occurrence in core is an *illustrative example inside a JSDoc comment* on the interface, not logic.)
- **`BackendPlugin` interface unchanged** — backends receive the provider via their factory (`createXPlugin({ database })`), not through a changed method contract.

**Honest residual (stated plainly):** the two custom migrate-runners' own `schema_migrations` bookkeeping DDL stays **inline** in `express/templates/src/migrate.js` and `python/templates/app/migrate.py` (still contains `TIMESTAMPTZ`). Reason: FastAPI's is a **3-line concatenated Python string literal**; tokenising it to one line would change the file's bytes and move the FastAPI hash — which a refactor must not do. This one statement is a clean **Day-5b** item (extracted alongside MySQL's variant, when a re-established MySQL hash makes restructuring safe). Every *substantive* dialect — entity-migration DDL, users-table DDL, types, and all drivers/image/connection — **is** behind the seam.
