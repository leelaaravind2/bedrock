## 1. How database selection works today (the trace)

Investigated this session:

- **The `database` field is inert.** `model.getSetting('database')` is **never read during generation** — it's a stored Phase-A answer (`'PostgreSQL'`) that nothing acts on. There is **no database plugin, registry, or dialect seam** (unlike `backend`, which the registry maps to a plugin).
- **Postgres is hardcoded in two places:**
  1. **Shell templates** (per backend): `docker-compose.yml` (`postgres:16-alpine`, `pg_isready`, port 5432), driver deps (`psycopg2`, `pg`, `jdbc:postgresql`, `org.postgresql`), connection config (`postgresql+psycopg2://`, `jdbc:postgresql://`, Django `ENGINE: django.db.backends.postgresql`), the **`V1__init.sql`** users-table DDL (Express/FastAPI), and the **migrate-runner** `schema_migrations` DDL.
  2. **Per-entity migration DDL** in the three SQL stacks' `buildMigration` (Spring, Express, FastAPI): `BIGINT GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMPTZ`, `DEFAULT now()`, `ALTER TABLE … ADD CONSTRAINT … REFERENCES`, etc.
- **Django is the outlier — dialect-agnostic.** Django uses ORM migration operations (`CreateModel`, `ForeignKey`); Django generates the correct SQL *per engine* at `migrate` time. Its only Postgres-ness is `settings.ENGINE` + the `mysqlclient`/`psycopg2` driver + the docker image. **No DDL codegen change is needed for Django + MySQL.**

**Conclusion:** the database is *not yet* a plugin. Day 5 introduces a clean **database-plugin (SQL dialect) seam analogous to the backend-plugin seam** (Laws 26–28: technologies are plugins), and routes the four backends' DB-specific output through it.

## 2. The design — a Database plugin (SQL dialect) seam

A new plugin **type**, mirroring `BackendPlugin`: a technology-neutral contract in `core/`, with Postgres/MySQL implementations in `plugins/`, selected by the composition layer from the model's `database` answer.

### 2.1 Interface (core-neutral; no Postgres/MySQL words in the core)

```ts
// core/plugin.ts — a generic SQL-dialect contract (no dialect specifics in core)
interface DatabasePlugin {
  readonly id: string;             // 'postgres' | 'mysql'
  readonly displayName: string;    // 'PostgreSQL' | 'MySQL'

  // --- DDL primitives the SQL-migration backends consume ---
  autoIncrementPkColumn(): string; // id column definition
  columnType(logicalType: string, opts): string;  // String/Text/Integer/Long/Decimal/Boolean/Date/DateTime → dialect type
  timestampColumn(name: string, opts): string;     // created_at/updated_at with dialect default
  fkConstraint(table, col, refTable): string;      // ALTER/inline FK
  createIndex(name, table, col, unique): string;
  usersTableDDL(): string;         // the V1 users foundation (dialect DDL)
  schemaMigrationsDDL(): string;   // the migrate-runner bookkeeping table

  // --- Shell/connection tokens the project shell substitutes ---
  dockerImage(): string;           // postgres:16-alpine | mysql:8
  healthcheck(dbName, user): string;
  port(): number;                  // 5432 | 3306
  // driver dependency + connection URL are provided as tokens per backend
}
```
(Exact surface is a Session-2 detail; the point is a small, generic dialect contract.)

### 2.2 Registry + selection (composition layer, not core)

`plugins/database-registry.ts` (analogous to `plugins/registry.ts`): `{ 'PostgreSQL': postgresDialect, 'MySQL': mysqlDialect }`, selected by `model.getSetting('database')`. The composition root passes the selected `DatabasePlugin` into generation alongside the `BackendPlugin`.

### 2.3 How backends consume it (the genuinely-needed wiring)

- `buildFileSet(model, backendPlugin, databasePlugin)` — the core generation entry gains a `DatabasePlugin` parameter (it receives a *handle*; it never learns which dialect — Law 25 holds). It threads the dialect into the backend's `generateProjectShell(model, db)` and `generateEntity(entity, ctx)` (context gains `database: DatabasePlugin`). This is a genuinely-needed, technology-neutral interface refinement — the same category as Day-1's relationship representation, not a leak.
- Each SQL-migration backend's `buildMigration` asks the dialect for the id column, types, timestamps, FK, and index strings instead of hardcoding them. The shell's `V1__init.sql` and migrate-runner DDL come from the dialect; docker image / healthcheck / port / driver / URL come from dialect tokens.
- **Django consumes almost nothing** — only the shell (ENGINE + driver + docker image/port) changes by dialect; its ORM migrations are untouched.

### 2.4 The determinism guard (the top risk — same discipline as relationships)

The refactor **must leave Postgres output byte-identical.** Method: create `PostgresDialect` that returns **exactly the current hardcoded strings** (extract, don't rewrite — e.g. `autoIncrementPkColumn()` returns the literal `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`; `usersTableDDL()` returns the exact current `V1__init.sql` bytes). With `database='PostgreSQL'` selected (the default), every backend emits identical bytes → **the four gates stay frozen**. `MySqlDialect` is the new branch. Diff Postgres output first, before adding MySQL.

## 3. MySQL-specific divergences to handle honestly

Keep the **logical schema identical** (same tables, columns, relationships) while the **dialect differs** — the Day-3 logical-vs-literal principle, now for databases.

| Concept | PostgreSQL (today) | MySQL 8 |
|---|---|---|
| Auto-increment PK | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `BIGINT AUTO_INCREMENT PRIMARY KEY` |
| Timestamp type | `TIMESTAMPTZ` | `DATETIME` (chosen over `TIMESTAMP`: wider range, avoids the 2038 limit; **honest caveat: no timezone** — app stores UTC) |
| Timestamp default | `DEFAULT now()` | `DEFAULT CURRENT_TIMESTAMP` |
| `updated_at` auto-update | app-level (`SET updated_at = now()` / ORM) | `… DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` (DDL-level; app also sets it — redundant, harmless) |
| Boolean | `BOOLEAN` | `TINYINT(1)` (`BOOLEAN` is a MySQL alias for this) |
| Decimal | `NUMERIC(19, 2)` | `DECIMAL(19, 2)` (`NUMERIC` is a MySQL alias) |
| String / Text | `VARCHAR(n)` / `TEXT` | same (utf8mb4 — a 255 VARCHAR is fine) |
| Integer / Long / Date | `INTEGER` / `BIGINT` / `DATE` | same |
| FK constraint | `ALTER TABLE t ADD CONSTRAINT fk_… FOREIGN KEY (c) REFERENCES p (id);` | **same syntax**; requires **InnoDB** (default in MySQL 8) and the referenced column indexed (PK ✓) |
| Index | `CREATE INDEX idx ON t (c);` / `CREATE UNIQUE INDEX …` | same |
| `schema_migrations` table (Express/FastAPI shell) | `… applied_at TIMESTAMPTZ DEFAULT now()` | `… applied_at DATETIME DEFAULT CURRENT_TIMESTAMP` |
| **Runtime placeholders (Express only)** | pg `$1, $2, …` | mysql2 `?, ?, …` — **the deep divergence** (runtime SQL, not just DDL) |
| Driver — FastAPI | `psycopg2` · `postgresql+psycopg2://` | `PyMySQL` · `mysql+pymysql://` |
| Driver — Django | `psycopg2` · `django.db.backends.postgresql` | `mysqlclient` · `django.db.backends.mysql` |
| Driver — Spring | `org.postgresql` · `jdbc:postgresql://` | `mysql-connector-j` · `jdbc:mysql://` (Hibernate auto-detects dialect) |
| Driver — Express | `pg` | `mysql2` |
| Docker image / healthcheck / port | `postgres:16-alpine` / `pg_isready` / 5432 | `mysql:8` / `mysqladmin ping` / 3306 |

**Honest MySQL notes:** FK enforcement needs InnoDB (MySQL 8 default); `DATETIME` drops timezone (store UTC); `now()` works as a function but a column DEFAULT must be `CURRENT_TIMESTAMP`; lowercase table names avoid MySQL's `lower_case_table_names` case-sensitivity trap. Django's ORM handles **all** of these automatically per `ENGINE`.

## 4. Scope — which backends get MySQL on Day 5 (honest effort)

There are two *handling shapes* (the database analog of Day-3's mechanism families):
- **Shape (a): ORM-abstracted** — Django. MySQL = shell/config only (ENGINE + driver + docker). Near-free.
- **Shape (b): explicit SQL DDL** — Spring, FastAPI, Express. MySQL = dialect-specific DDL via the seam. Within (b): FastAPI/Spring runtime SQL is abstracted (SQLAlchemy / Hibernate) so only DDL + connection change; **Express additionally needs `$N` → `?` runtime placeholders** — the deepest change.

**Day 5 (design + core wiring) — a representative subset proving both shapes:**
- **Django** (shape a) — proves DB selection routes end-to-end via shell/config with minimal risk.
- **FastAPI** (shape b, runtime-abstracted) — proves the `SqlDialect` seam generates correct MySQL DDL for entities + relationships and wires the connection. This is the meaty proof of the dialect abstraction; Spring is the same DDL shape.

**Deferred to Day 6 (prove-across-stacks + dropdown):**
- **Spring** (same DDL shape as FastAPI — mechanical once the seam exists) and **Express** (adds the runtime-placeholder divergence — done deliberately, not rushed).
- The **database dropdown** wiring + the **four-stack MySQL cross-proof**.
- The **live MySQL boot** (`docker compose up` a MySQL project, confirm migrations apply and related data + FK enforcement work) — mirrors relationships' static-then-live cadence (Days 1–3 static, Day 4 live). A quick Day-5 spot-boot of FastAPI+MySQL is optional if time; the committed live proof is Day 6.

This staging is honest about effort and de-risks Express (the hardest) into its own focused step.

## 5. Determinism & baselines (blocking gates)

- **Postgres output byte-identical (the four frozen gates):** selecting `database='PostgreSQL'` must still produce Spring `010098cd…`, Express `a437a302…`, FastAPI `dca2254f…`, Django `68601cc5…`. Guaranteed by `PostgresDialect` returning the exact current strings (§2.4). This is the blocking gate — diff Postgres first.
- **MySQL generation deterministic:** for each Day-5 MySQL-covered combination (Django + FastAPI, × DemoApp + TeamTracker), generate twice → byte-identical; **establish and record** the new MySQL hashes. New axis: hashes are now per `(backend × database × model)`.
- **No AI / randomness / timestamps** in the generation path (ADR-001/003). Dialect selection is a deterministic switch (same model → same output).

## 6. Reuse & neutrality (Law 25)

- **Reuse the existing entity + relationship representation unchanged** — the dialect only changes *how* the same logical schema is emitted, not *what* the model holds.
- **Core stays technology-neutral:** the core defines the generic `DatabasePlugin` contract and threads a dialect *handle* through generation; it contains **no** Postgres/MySQL SQL. All dialect specifics live in `plugins/database/postgres` and `plugins/database/mysql`. The `database` field is already a neutral string.
- **The one genuinely-needed interface refinement:** `buildFileSet` + the backend generation context carry the selected `DatabasePlugin` (analogous to how they carry `multiUser`). Justified and neutral — not a leak.
- **No `BackendPlugin` behavioral change** beyond receiving the dialect; backends keep the same five-member contract shape.

## 9. Risk notes (for Session 2)

- **Postgres byte-drift from the refactor is the #1 risk** — extracting hardcoded DDL/shell strings into `PostgresDialect` must reproduce them *exactly* (whitespace, alignment, `now()` vs `CURRENT_TIMESTAMP`, the `V1__init.sql` bytes). Diff all four Postgres DemoApp outputs before writing any MySQL code; a moved gate means the extraction wasn't faithful.
- **The `V1__init.sql` / `schema_migrations` shell DDL** is the trickiest extraction (static template → dialect-provided content) — must byte-match for Postgres.
- **Interface-refinement blast radius** — adding a `DatabasePlugin` parameter to `buildFileSet` and the demos/CLI/UI callers must be threaded through without changing output; default callers select Postgres.
- **Express deferred deliberately** — do **not** start the `$N`→`?` runtime-placeholder change on Day 5; it's Day 6's focused work.
- **Honest MySQL semantics** — state the `DATETIME`-drops-timezone and InnoDB-required notes plainly; don't imply byte-identical SQL across dialects, only identical *logical* schema.
